# Conformance suite для SIPL

Набір тестових програм з очікуваними результатами (AST, кінцевий стан, помилки), який
перевіряє, чи відповідає реалізація мови SIPL її специфікації.

Набір не залежить від конкретної реалізації: `runner.py` не імпортує пакет `sipl`, а
запускає реалізацію як окрему програму через її командний рядок і порівнює JSON-вивід з
очікуваним. Тому ним можна перевірити будь-яку реалізацію (на будь-якій мові), яка
підтримує описаний нижче інтерфейс.

## Запуск

```bash
python conformance/runner.py                         # перевірити команду `sipl`
python conformance/runner.py --cmd "python -m sipl"  # інша команда запуску
python conformance/runner.py -v                      # показати й успішні випадки
python conformance/runner.py --cases інша/папка      # інший набір випадків
```

Потрібен лише Python 3.11+ (без сторонніх пакетів). Код завершення: `0`, якщо всі
випадки пройшли, `1`, якщо хоча б один не пройшов або випадків не знайдено.

Приклад виводу при помилці:

```
FAIL  run/power
      $.state: expected exactly {"R": 1024, "X": 2, "Y": 0}, got {"R": 512, "X": 2, "Y": 0}
28 passed, 1 failed, 29 total
```

## Що вимагається від реалізації

Реалізація має підтримувати такий виклик (повний опис - у [docs/cli.md](../docs/cli.md)):

```
<команда> check|parse|run ФАЙЛ --json [--set ІМ'Я=ЧИСЛО ...] [--max-steps N]
```

- друкувати в stdout один JSON-об'єкт з полями `status` (`ok`/`error`), `error`
  і полями команди (`ast` для `parse`, `state` для `run`);
- завершуватися кодом: `0` - успіх, `1` - синтаксична помилка, `3` - помилка виконання,
  `4` - перевищено ліміт кроків.

## Формат випадку

Кожен випадок - це два файли з однаковою назвою в підпапці `cases/`:

- `НАЗВА.sipl` - програма;
- `НАЗВА.json` - що з нею зробити і що очікується.

```json
{
  "description": "Степінь: R = X^Y",
  "command": "run",
  "initial_state": {"X": 2, "Y": 10},
  "max_steps": 1000,
  "expect_exit": 0,
  "expect": {"status": "ok", "state": {"R": 1024, "X": 2, "Y": 0}}
}
```

| Поле | Обов'язкове | Значення |
|---|---|---|
| `description` | ні | що перевіряє випадок |
| `command` | так | `check`, `parse` або `run` |
| `initial_state` | ні | початкові значення змінних (передаються як `--set`) |
| `max_steps` | ні | ліміт кроків (передається як `--max-steps`) |
| `expect_exit` | так | очікуваний код завершення |
| `expect` | так | очікуваний JSON-вивід (див. правила порівняння) |

Назва випадку у звіті - шлях без розширення: `run/power`, `syntax/missing_else`.

## Правила порівняння

`expect` порівнюється з фактичним JSON-виводом **частково**:

- кожен ключ з `expect` має бути у виводі з таким самим значенням;
- зайві ключі у виводі ігноруються. Тому випадок може не вказувати `span` вузлів AST,
  текст повідомлення про помилку чи `end_line`/`end_column` позиції;
- вкладені об'єкти порівнюються за тими самими правилами;
- списки мають бути однакової довжини й збігатися поелементно;
- `true`/`false` не дорівнюють `1`/`0`.

**Виняток: `state` порівнюється точно.** Кінцевий стан має містити рівно ті змінні й
значення, що в `expect`, без зайвих змінних.

Отже, набір перевіряє лише те, що визначає мова: результат виконання, структуру AST,
етап і позицію помилки. Формулювання повідомлень, кількість кроків і подібні деталі
реалізації не перевіряються.

## Групи випадків

| Папка | Команда | Що перевіряє |
|---|---|---|
| `syntax/` | `check` | коректна програма; синтаксичні помилки та їхні позиції |
| `parse/` | `parse` | форма AST: пріоритети, асоціативність, межі операторів, від'ємні числа |
| `run/` | `run` | кінцевий стан; помилки виконання та ліміт кроків |

Окремі випадки фіксують рішення щодо семантики, які мають однаково виконувати всі
реалізації:

- `run/undefined_variable` - читання змінної без значення є помилкою;
- `run/disjunction_evaluates_both_sides` - `∨` обчислює обидві частини;
- `run/unbounded_integers` - цілі числа необмежені;
- `syntax/unary_minus` - унарного мінуса немає.

## Як додати випадок

1. Покладіть `НАЗВА.sipl` і `НАЗВА.json` у відповідну підпапку `cases/`.
2. Запишіть очікування з урахуванням специфікації мови (не копіюйте вивід реалізації,
   яку перевіряєте).
3. Запустіть `python conformance/runner.py -v`.

Набір також запускається автоматично в тестах проєкту (`tests/test_conformance.py`).
